# marketing: lead-generation features (this repo only)

Everything in this folder exists only in the marketing repo. Nothing here is core, and nothing here is ever ported upstream. The plan behind it is https://claude.ai/artifact/TE43jqJa9kYRe37fMBsANn.

## Guardrails (from the plan; they bind code, copy, ads and emails)
- **No results-based audiences.** Never send results, patterns, scores, item responses or care flags to an ad platform, analytics tool or email tool, and never build an audience, segment or list from them. Analytics events and synced contacts carry no result data.
- **No promotional email for FLOODED results.** A person whose pattern is FLOODED gets no promotional message: no program invite, no live-session invite, no nurture sequence. The results page already hides `ProgramInvite` for them; every new marketing surface (web or email) must check the pattern the same way.
- **Separate marketing consent.** Nurture emails need their own checkbox on the start screen, separate from the results consent and the newsletter. Its wording is **DRAFT pending a lawyer**: ship nothing that sends nurture email until the lawyer approves it. It is logged with the policy version, like the newsletter consent. (Not built yet: it touches core paths, see `UPSTREAM-REQUESTS.md`.)
- **Opt-in sync sends only email, locale and source.** When opt-ins are synced to an email tool, the payload is exactly `{ email, locale, source }` (source = utm/ref attribution). Never name, never scores. Deleting through the existing delete link must remove the contact there too. (Not built yet: core paths.)
- **Partner links use `?ref=CODE`.** A partner shares `/{locale}?ref=CODE`. Codes are lowercase letters, digits and hyphens, 2–32 characters (`REF_CODE` in `validation.ts`). Counts per code are aggregates only.
- Also from the plan: never market to anyone under 18 or remove the age gate; never make results shareable (sharing shares the landing URL only); never treat the institute copy as a sales list; never describe the map as validated, clinical, diagnostic or a cure, in any language; never use testimonials without written consent.

## Layout
- `config.ts`: `MARKETING_POLICY_VERSION` and `PUBLIC_POLICY_VERSION` (`<core version>+<marketing version>`), recorded with public-mode consent by `StartScreen` and `EmailResultsForm`. `PROGRAM_URL` (program page per locale; PLACEHOLDER, all the homepage until the institute supplies them) and `LIVE_SESSION_URL` (next "Reading your map" session per locale; empty hides the link) are edited here and ship with a deploy. Bump `MARKETING_POLICY_VERSION` whenever the marketing privacy section changes after a version has been deployed (`m2026-10-draft` has not been deployed yet, so drafts before launch keep it).
- `validation.ts`: zod schemas for marketing request fields (`attributionSchema`, `parseEmailMarketingFields`, `REF_CODE`, `UTM_VALUE`). utm values are slugs (`^[a-z0-9][a-z0-9._-]{0,63}$`, lowercased) so a link cannot carry a name or subscriber id; m0001 enforces the same pattern.
- `attribution.ts` (browser): reads utm_source, utm_medium, utm_campaign and ref from the URL into memory (last touch wins). Only when the person submits the start form (`commitAttribution()` in `StartScreen`) is it written to localStorage (`ism:mkt:attribution:v1`, 30 days), so nothing is stored on the device before consent. `attributionRequestFields()` adds it to the results request. `components/AttributionCapture.tsx` runs it on every page of the locale layout, so partner links and ads that land on `/start` count too.
- `analytics.ts`: Vercel Web Analytics custom events (cookieless). `FUNNEL_EVENTS` is the closed list: `landing_view`, `start`, `completion`, `email_sent`, `invite_click`. `eventProps()` copies only `locale`, `ref` and `target`, so no caller can send anything else. `analyticsBeforeSend`/`sanitizeUrl()` drop every URL outside the public pages (`/{l}`, `/start`, `/questionnaire`, `/results`, `/privacy`, `/results-deleted`; cohort, facilitator and admin URLs carry record ids) and reduce the rest to the path plus the utm/ref values that pass validation. `trackFunnel()` creates the `window.va` queue itself with `beforeSend` as its first entry, because `<Analytics>` hydrates inside a Suspense boundary after page effects: `track()` silently drops events until the queue exists, and the script must see the sanitiser before any queued event.
- `links.ts`: `programInviteUrl(locale)` and `liveSessionUrl(locale)` tag outbound links with `utm_source=inner-system-map`, `utm_medium=results`, `utm_campaign=program-invite|live-session`, `utm_content=<locale>`; `partnerLink(origin, locale, code)` builds `/{locale}?ref=CODE`.
- `components/ShareTheMap.tsx`: "Share the map" on the public results page (rendered by `ResultsView` inside the `actions` section, not when FLOODED). It shares `shareUrl(origin, locale)` = `/{locale}?utm_source=share` through the Web Share API, or copies it; strings under `marketing.share`. It never shares anything from the attempt.
- `funnel.ts`: `funnel(event, { target? })` is the one call the app's hooks make; it adds the page locale (`<html lang>`) and the stored partner code.
- `components/MarketingAnalytics.tsx` (in the locale layout) renders `<Analytics beforeSend>`; `components/LandingView.tsx` (on the landing page) sends `landing_view`.
- Partner links and counts: admins register partner codes at `/{locale}/admin/partners` (`components/RegisterPartnerForm.tsx` → `server/partner-actions.ts` `registerPartner`, zod `registerPartnerSchema`, `withUser`; RLS lets admins only), and the page lists each partner's `/{locale}?ref=CODE` links (`components/PartnerLinks.tsx`). `removePartner` (`components/RemovePartnerButton.tsx`) deletes a partner and its label, which may name a person; the code's past counts stay. Both actions check the admin role first, and RLS checks it again. `funnel("start" | "completion")` POSTs `{ event: "start" | "complete", ref? }` (keepalive) to `app/api/marketing/funnel/route.ts` (zod `funnelCountSchema`, 10 per client per hour), which calls `server/funnel-counts.ts` `incrementFunnel()`: one row per day, code and event in `marketing_funnel_counts` (m0002). Only registered codes get their own row; no code counts under `''`, any other code under `'-'`, so visitors can neither grow the table nor store their own strings. It writes on the service connection (anonymous, no personal data). `listRefCounts(userId)` reads through `withUser`. The retention cron calls `pruneFunnelCounts()` (rows older than 400 days) in its own error handler, so a marketing failure never marks the core retention run as failed. The counts come from browsers and are untrusted: compare channels with them, never pay partners from them.
- `server/attribution.ts`: `saveResultAttribution(id, a)` writes the m0001 columns on the opt-in `public_results` row through `asService` (the same connection as the public insert). `ref_code` is stored only when the code is registered in `marketing_partners`; otherwise it is null. It never throws.
- `components/MarketingPrivacy.tsx`: the marketing section of the privacy notice (strings under `marketing.privacy`, DRAFT pending legal review), rendered after the core sections by `app/[locale]/privacy/page.tsx`. Every new marketing data use gets a paragraph here and a `MARKETING_POLICY_VERSION` bump.
- `UPSTREAM-REQUESTS.md`: core changes marketing needs, written for the upstream repo. Remove an entry once it has been ported.

Hooks into non-core app files (keep them one line each): `app/[locale]/layout.tsx` (AttributionCapture), `components/questionnaire/StartScreen.tsx` (commit attribution, policy version), `components/results/AutoEmailStatus.tsx` and `EmailResultsForm.tsx` (attribution in the body, policy version), `app/api/public/email-results/route.ts` (parse and store), `app/[locale]/privacy/page.tsx` (marketing privacy section), `app/[locale]/page.tsx` (LandingView), and the funnel calls: `StartScreen` (start, public mode only), `Questionnaire` (completion, public path only), `AutoEmailStatus`/`EmailResultsForm` (email_sent), `ProgramInvite` (invite_click). `components/results/ProgramInvite.tsx` itself is rewritten here (program and live-session links from `links.ts`, live-session strings under `marketing.invite`); `ResultsView` still hides it for FLOODED and cohort results. `ResultsView.tsx` also renders `ShareTheMap` inside the `actions` render (a new results section would change `sections.ts`, which is core).

## Rules for code here
- Marketing request fields (utm_*, ref, marketing consent) are parsed by `validation.ts` inside the routes, next to the core schema. Never extend `lib/validation/`. Invalid marketing fields are dropped; they never fail the core request.
- Marketing UI strings live under the top-level `"marketing"` key in `messages/{en,es,ro,tr}.json`, in all four locales (ES/RO/TR are drafts). The locales test checks key parity and forbidden words for them too.
- Marketing tables and columns come from `db/migrations/m0NNN_*.sql`, and they are **additive only**: new nullable columns or new tables. Never drop, rename or change core columns, constraints, policies or functions. This repo is expected to take over the production database while the original may still be running on it.
- Database: develop against the `marketing-dev` Neon branch only (from the original project's dev branch). Never copy the original's `.env.local`, never connect this repo to the original's Vercel project, never run `npm run db:migrate` against anything but `marketing-dev`. Only one live app may run against a database.
- Browser storage is wrapped in try/catch; a blocked storage never breaks the page. Nothing marketing-related is written to the device before the start-form consent.
- Every new data use is described in the marketing privacy section, with a `MARKETING_POLICY_VERSION` bump. The wording is DRAFT until the lawyer reviews it.
- A new analytics event goes into `FUNNEL_EVENTS` and the privacy section's analytics paragraph. Never add an event property beyond locale, ref and target.
- `asService` in marketing code is allowed only for the anonymous counter and the opt-in public result columns. Anything a signed-in person does goes through `withUser`.
- Never log attribution together with an email, name or result. Log the outcome and reason only.
